# PixelForge 正式游戏移植版

使用 starry_demo/start_PixelForge.cmd，交付目录 advanced_demo/delivery/PixelForge。加载 PixelForge.elf 与同目录 assets.json。高级版只保留 PixelForge 和 lunaria_stress 两个交付模式。

## 移植内容

- 复用第三轮已完成时序验证的 v13（0x000D0000）硬件，100 MHz，8 KiB纹理缓存、按数据拍有效位填充、连续缓存读取；任意整数像素位置保留。
- 正式游戏连续命令只有在操作、源地址、步长、尺寸和Alpha全部相同时才复用描述符，仅更新坐标。混合弹型、出生渐入Alpha、裁剪或尺寸变化都会走完整提交。保留队列等待、fence、错误/超时检查和帧末命令数核对。
- 恒速直线弹在出生时预计算每步位移，使用与旧版相同的定点舍入。花瓣、旋转、追踪、加速、停顿重瞄及激光仍用原算法。
- 缓存存活弹数，分配/离场/碰撞/清场同步更新，减少反复扫描。保留原槽位遍历、分配和绘制顺序，没有采用压力版末尾交换回收，以免改变重叠混色与碰撞顺序。
- 正式弹状态从28字节压至24字节：年龄/寿命和类型等小范围字段合并存储，保留原1000tick寿命及1001tick退休。启用Os和LTO降低代码占用；没有缩小原8192字节栈。
- 容量从640提高到1024；设置窗口增加768/896/1024，可输入64–1024任意整数。SPRITE与结算峰值支持四位数。默认256。
- 标题图集和战斗HUD的LUNARIA改为PixelForge，新启动窗口也显示PixelForge。内部既有调试邮箱/符号名称保留，保证加载器协议兼容；这些不是游戏显示名称。

敌弹仍为16×16贴图，圆弹可见外轮廓保持10×10，碰撞阈值保持距离平方<20。圆弹中央近白核心从24像素小幅缩至16像素，外围明亮主体保留更多本色；同一圈薄光晕的Alpha从48提高至80，不扩大外轮廓。四种主题颜色更容易区分。锥形弹、玩家弹及其判定不变。

中文名为“像素熔炉”。正式激光改为沿轴向连续的约10px粉白亮芯、两侧有色主体及每侧约6px渐淡光晕，整体约32px宽，碰撞半径仍为15px。原预警、射向、持续时间及发射节奏不变，发出端增加同色光晕圆弧端帽，远端维持原样。

旧方案每12px重复绘制32×32圆片，反复混合相同像素，亮斑重叠后看起来整柱发白。新方案沿主轴使用互不重叠的8px短条，横截面始终由亮芯向两侧光晕过渡。每条的位置按真实射向计算，仅短条内部斜率选用17种预制纹理，方向误差不会随射程累积。裁去透明边缘、保持2560字节纹理步长和描述符复用。没有扩大图集、增加运行时贴图生成或修改硬件。

为容纳方向短条，八帧命中特效在图集内搬迁，图像逐像素保持相同；播放器、锥形弹和Boss素材保持。软件、图集必须配套更新。

Boss从激光预警出生到最后一束激光消失保持静止；多束激光分别到期时，以所有激光的active状态共同决定解冻。运动时钟扣除冻结时间，消失后沿暂停轨迹继续移动，避免快进跳位。玩家仍可移动开火，游戏时间与其他弹幕照常推进。新改动仅对PixelForge生效。

## 上限与节奏

保持原逻辑：高于256时主要按设置上限等比增加每轮弹数，花瓣/星形按完整图案单位取整；低于256才放慢发射间隔。原640档的12.5%密度补偿保留在640档，不转移到新的最大档。不强制补满弹池，也不改变图案演出间隔和整组准入/延后规则。1024表示容量，实际可见数量会随阶段变化。

压力版1855发稳定60FPS是用户已测参考，但压力版用8×8单一弹型；不能据此声称正式16×16、多弹型、激光的稳定上限。PixelForge尚未上板测量。

阶段血条：击破阶段后，预警期间按下一阶段完整血量计算剩余总血条，避免阶段编号先增加、实际hp尚未补满造成先缩短再恢复。预警结束血条长度保持，下一次有效受击正常扣血；实际战斗HP、计分和过渡时长不变。

## 本地验证

- 七次阶段切换逐帧验证实际血条绘制宽度：预警期间与进入战斗后保持一致，预警不受击，新阶段受击后正常下降，最终击破归零。
- 非激光阶段、无敌模式下，旧版与PixelForge的57600个逻辑步轨迹摘要一致；激光冻结和圆弹判定变化另外进行定向验证。
- 真实1024容量模拟153600步，独立扫描验证缓存计数和上界。
- 激光定向测试验证预警至1800ms消失、不同到期时间的多束激光、实际发射出生点、玩家自由移动、解冻恢复且首步无跳位。
- 验证圆弹4px距离命中/5px距离不命中，以及锥形/菱形5px判定保留；圆弹16×16贴图中可见轮廓10×10，近白核心16像素、半透明光晕至多28像素。
- 除圆弹、激光短条、命中特效搬迁及标题所需区域外，图集与旧版逐字节一致；八帧命中特效搬迁前后逐像素一致，GUI/ELF/素材/容量检查通过。
- 256个射向逐像素检查亮芯连续、两侧有色半透明光晕、短条之间不重叠及硬件源地址/宽度对齐。相同中心位置的全方向激光采样绘制量从5,823,096降至2,544,936像素，减少56.3%。
- 从真实渲染器提取命令，在现有v13 Alpha引擎RTL中回放横向、45°、67.5°、纵向四种激光，启用总线停顿及20周期源读取延迟，逐像素核对输出。冷/热缓存绘制周期减少约44%～63%；暖缓存横向65,733→36,922，45° 72,392→26,851，67.5° 54,493→21,202，纵向48,360→17,696。
- 上述为激光绘制量和加速器仿真，不是整帧FPS测量；短条命令数略增，CPU提交、显示刷新及真实DDR竞争仍需实板验证。保持1024容量、原8192字节栈和原v13硬件；当前OCRAM栈顶外剩余16字节，链接检查通过。

## 上板步骤

1. 使用Efinity Programmer烧录本目录ti60f225_oob.bit，然后退出Programmer。与压力第三/四轮使用相同v13硬件，本轮圆弹和激光图集已改变，需要重新配置清除旧封存素材；旧正式v12 bit不能直接加载本版ELF。
2. 双击start_PixelForge.cmd，选择PixelForge.elf、正确串口并连接/加载，等待素材完整校验。标题英文为PixelForge、中文为“像素熔炉”；普通敌弹仍为16×16贴图，圆弹可见主体略小。
3. 先用256/640观察四种圆弹颜色差异及薄光晕；确认锥形弹和玩家弹外观保持。第7/8阶段检查激光沿轴向的连续亮芯、两侧彩色光晕，以及预警及发射期间Boss静止，最后一束消失后平滑恢复。再测768→896→1024；SPRITE显示游戏元素总数，实际敌弹数不必达到配置上限。
4. 性能测量先开启无敌调试，Alpha保持255，进入要测的阶段并预热5秒，启动60秒测量。正式版测量保留原行为：暂时屏蔽射击和暂停，避免提前结束阶段。
5. 分别关注花瓣/旋转、追踪、组合弹幕和激光阶段，记录最低FPS、最慢绘制时间、超预算帧、重复帧和错误增量。游戏稳定性以最重阶段为准，不以某一时刻B数量为准。

## 重建

在advanced_demo目录：

```powershell
python -B scripts/build_pixelforge.py
# 已初始化MSVC的终端
python -B scripts/run_pixelforge_checks.py
```

使用既有RISC-V工具链、Python/Pillow和Windows字体。构建从 design/game_assets 读取共用基础图集、背景与清单，从压力版交付目录读取已校验的 v13 bit；不依赖已删除的旧模式。共享源码的移植改动由 PIXELFORGE 宏隔离。无需重新生成 IP。

## 战斗HUD排版更新

PixelForge下方同一行显示SPRITE（当前游戏元素总数）和FPS，移除A/B及MAX。左下角LIVES后接生命图标，右下角分数前标注SCORE。Boss总血条左侧显示剩余百分比，向上取整使非零血量至少显示1%；沿用跨阶段连续的总血量口径。阶段名称以16px字距排版，移除阶段名称右侧的ROSE花瓣数字。

本轮同时更新发射端图集：需重新配置现有v13 bit清除旧素材，再通过原CMD加载配套ELF及assets.json。无需重新编译硬件。

## 发射端与HUD细节

激光圆弧端帽中心位于距发射点74px处，半径16px，靠Boss的最外侧距半径约51px的外环约7px；整数像素取整会有约1–2px误差。端帽沿用光柱的亮芯、彩色主体与渐淡光晕。交界短条采用4px分段及朝前半平面裁剪，避免斜向光柱露出直切角，后续主体继续使用8px短条。

LIVES上移5px，与生命图标对齐；战斗SCORE改为五位，移除原先最左侧两个固定零。为容纳端部裁剪代码，HUD数字绘制复用既有格式化函数，并限制渲染入口内联；保持Os/LTO和8192字节栈。原战斗逻辑与激光判定保留。

256个方向检查Boss与端帽之间的透明间距、圆弧光晕、端帽后侧角点透明及亮芯连续。最新像素量和RTL周期见checks.json，前述性能数字为上一轮光柱优化基线；本次尚未上板测量FPS。
