# 2026-10-26 满载性能交接与下一步方案

## 当前结论

建议先封存当前可重复的 30 FPS 版本并共享给队友，再做有对照的软件优化。
保留 48 敌机、64 敌弹作为压力基线，不先降低负载，也不删掉用户提供的图片。
首要目标是把逻辑、命令提交、绘制和换帧申请压进 16.667 ms，绘制最好控制在 14–15 ms。
满载稳定 60 FPS 尚未达成；这一版可作为阶段成果上传，不能作为最终性能验收完成版。

## 已完成的内容

- 基础 A–E 有历史实板验收记录，基础工程继续独立保留。
- BLIT、Color Key、Alpha 已接入，当前游戏保留队伍飞机、子弹、爆炸及整幅海岛背景。
- HDMI 保持 1920×1080@60 Hz；游戏视口为中央 640×480@(640,300)。
- 两个物理缓冲分别初始化海岛背景；中央每帧恢复，外围保持静止。
- v7 有 8 项绘图命令队列，CPU 可以继续提交命令，帧末统一排空；显示保护保留。
- 原 1080p ELF 未覆盖；居中版独立构建与打包，并有专用调试启动脚本。
- 前一轮已通过交叉编译、OCRAM 链接、三种显示/背景组合的主机检查、100 秒满载逻辑模拟、
  UART 检查、22 项桌面调试检查及 OpenOCD 离线解析。本轮仅分析和记录，没有改动绘图实现。

## 为什么稳定在 30 FPS

在双缓冲与垂直同步下，当前绘制跨过下一个 16.667 ms 边界，只能在再下一个边界换帧，
所以稳定呈现 33.333 ms / 30 FPS。最慢绘制从 27.134 ms 降到 16.667 ms，至少需降低
约 38.6%；考虑绘制之外的游戏逻辑和提交换帧余量，实际应以 14–15 ms 为优化目标。
因此需要明显降低每帧工作量，但不能直接按“FPS 翻倍，所有逻辑必须快一倍”估算。

写节流高说明图形写事务长期被保护策略挡住，不能直接解读成 DDR 物理带宽耗尽。
`ddr_write_admission.v` 的当前政策是：显示活跃期间，一次写事务完成后清空读配额，
通常需再收到 128 个显示读 beat 才放行下一次写；短至 4 beat 的字形行写和长至
32 beat 的背景行段写都会消耗一次放行。reader_safe 等条件有旁路，不能把这个关系
当成全程严格的理论吞吐上限。

只增加命令队列深度不能减少像素流量或写事务。当前帧末等待短也不能证明 CPU 是瓶颈：
硬件等待可能已经发生在队列满时的提交循环里。

## 优先级 1：软件减少重复背景和 HUD 工作

1. 把 HUD 与中央游戏区的恢复分开。当前 `restore_centered_island_background()` 每帧
   恢复 307,200 像素，随后 `render_hud()` 在 `!GAME_FULLSCREEN` 分支强制缓存失效，
   重新覆盖面板并画字。先让游戏区恢复跳过顶部 HUD 带，再恢复按物理缓冲独立的 HUD 缓存。
   字段可按 250 ms 或变化更新；切场景、首次使用、离开自测时强制刷新。
2. 截图实时样本有 45 次字形绘制。16×21 字形在当前引擎中每行至少一次写事务，
   即该样本约 945 次短行写，哪怕颜色键全透明也保留 AW/W/B 事务。
   这只是样本估计，不能作为区间平均收益承诺。
3. 在居中版接入按物理 Back 保存的损伤区域。恢复该物理缓冲上次精灵/效果/覆盖文字占用
   的区域，再重画当前精灵，不能只恢复“上一帧”的位置；Back 通常隔一帧才被重用。
   相邻区域只在能减少实际 burst 时合并，密集场景回退到整个游戏区恢复。
4. 每帧中央背景复制的读写有效载荷为 2,457,600 字节，若每秒 60 帧为 147.456 MB/s。
   这是有效字节数，不含协议和切换开销。只看写 burst，背景每帧至少约 2,400 次，
   约为本轮平均写事务的 36.5%；4 KiB 拆分可能增加事务。
5. 裁掉精灵全透明外边缘时更新图集源矩形和目标偏移，保持位置及命中区；X/width 保持
   DMA 对齐。不要只把 Alpha 设为 0：当前 Alpha 引擎仍会走源读取、背景读取和写回。

每项单独建立新 ELF 和 manifest，沿用同一 v7 bit，完整测 60 秒。比较 FPS、最慢绘制、
写 burst、背景像素和写节流。不能预先保证这一轮软件改动就能达到满载 60 FPS。

## 优先级 2：针对短事务的硬件服务优化

若软件减少恢复/HUD 后仍不达标，优先讨论写准入按实际 burst 长度计费，或允许在安全水位
内使用有上限的累计信用；保留显示低水位优先、滞回、已暴露 AXI VALID 和完整事务保护。
不能简单关闭准入，也不能仅把 READ_QUOTA 从 128 改小后直接发布。
软件 `accel_init()` 当前硬编码检查 quota=128 与水位常数，硬件策略变化需要能力/版本、
API、寄存器说明和回归同步修改。

后续再考虑减少 `WR_LOAD/WR_DATA` 气泡、Alpha 连续流水、源/背景/写回的分段重叠，
以及多个 outstanding 读事务。这些会改变缓冲与 AXI 所有权处理，应独立实验。
v7 已有 XLR 90.22% 使用率，避免同时堆叠多个大模块后再定位问题。

## 负载降级与最大稳定负载

可以另外测 48/64、36/48、24/32、12/16（敌机/敌弹），每档 60 秒，找到稳定 60 FPS
的最大负载。它们是待测档位，不是已有达标结果，也不能由 30 FPS 线性推算。
当前“满负载场景”固定补足 64 敌弹，测量入口要求敌机上限为 48；仅在 UI 调低敌机上限
不能完成规范的分档测量。需要显式增加可变压力配置、保存两种数量及测量类型，同时保留
原 48/64 的压力入口和验收口径。降低默认游戏难度可以用于演示，但不能标记成原满载达标。

## 协议参考

Arm AMBA AXI/ACE 协议规范 IHI0022H 的握手与事务要求是后续硬件实验的约束：
VALID 暴露后不能在等待 READY 时随意撤回或改变载荷；INCR burst 不能跨越 4 KiB 边界。
规范：<https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf>
这些协议规则不能代替本项目显示 FIFO 安全水位和板端回归。
