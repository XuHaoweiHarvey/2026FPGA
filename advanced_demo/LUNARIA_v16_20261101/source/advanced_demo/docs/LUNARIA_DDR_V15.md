# v15.1 单请求 DDR 兼容修订（2026-10-31）

用户在初版 v15 上板后报告 EA05，背景第 10 个 4 KiB 块（字节偏移 0x9000）回读校验失败。随后 JTAG 连硬件 ID 都读回零，无法继续以该状态确定根因。不能把这一结果解释为已经证明 DDR 带宽不足、程序损坏或用户选错 ELF。

本次交付将 READ_OUTSTANDING 固定为 1，使用与 v14 相同的共享读取分支；保留透明边缘跳过、双结果缓冲和完整画面。源之后的目标请求可提前准备，但 DDR 只接受一个未完成读请求。该修订是隔离并发读取兼容性的候选版本，尚未上板证实消除 EA05。

硬件 ABI 保持 0x000f0000/0x0007fffb，配套 ELF 内容未改变。目录仍为 hardware/v15；请用 SHA256SUMS 和 source_manifest 的 revision/read_outstanding 区分初版。必须重新配置新 bit，再加载配套 ELF；仅重开窗口无法替换 FPGA 电路。原包保存在 output/lunaria_v15_initial_delivery。

新增测试用真实 CPU-DDR 桥接模块及共享仲裁，执行背景和图集共 24 个 4 KiB 块（98304 字节）的逐字写入/回读，显示端并行请求数据。行为级 DDR 不能验证厂商加密控制器的实际上板兼容性。

v15.1 的最终时序见 verification/hardware-v15-checks.json；实际整帧对比见 verification/trace-v15-checks.json。下文数值属于初版历史，不能直接当作 v15.1 性能。

# LUNARIA v15 DDR 优化

目标是在完整保留画面和混合顺序的前提下提高稳定 60 FPS 的元素容量。450 不是设计目标，也不承诺硬件能无限增加元素。

## 本次实现

- 共享读仲裁从一个未完成请求改为最多四个，固定 ID0，按请求顺序归属响应；显示低水位优先。DDR 控制器可以通过 ARREADY 限流。厂商加密控制器实际允许的并发深度仍需上板测量。
- 源贴图读取接受后，提前提交同段目标读取，重叠地址和首拍等待。
- 在原有不可变贴图缓存中记录每四像素的透明标记。命中缓存时跳过全透明行、裁掉两侧全透明块。只认 alpha=0 或全局 alpha=0；任何非零光晕都保留，中间透明块仍保持原混合顺序。缓存未命中、失败填充、地址冲突不使用旧标记。
- 保留 v14 双结果缓冲和命令间写响应屏障。不同命令不能提前读取尚未写回的目标。
- 新增八项读取细分计数，快照从 21 字扩展为 29 字，旧版本保持 21 字。

## 性能计数

硬件版本 0x000f0000，能力位 0x0007fffb。E8 写一次原子锁存；读 E8 返回字数。100–150 保持原 21 字。新增：

| 地址 | 内容 |
|---|---|
| 154 | 源地址等待周期 |
| 158 | 目标地址等待周期 |
| 15C | 源首拍等待周期 |
| 160 | 目标首拍等待周期 |
| 164 | 源后续数据等待周期 |
| 168 | 目标后续数据等待周期 |
| 16C | 源读取 burst 数 |
| 170 | 目标读取 burst 数 |

100 MHz，每项按 2^32 回绕。目标首拍等待包含排在源请求后面的时间，不能与其他等待简单相加。计数覆盖 Alpha/激光引擎，不覆盖全部背景复制、显示读取或 CPU DDR 流量；读等待高不等于证明 DDR 总带宽耗尽。错误排空期间细分计数不用于性能推断。

提交/背压时间包含硬件绘制过程中队列满的等待，以及分页等待，不能据此认定队列太浅。5 秒 DDR 采样起止会暂停 CPU，60 秒帧率验收须另测。

## 验证及边界

verification/trace-v15-checks.json 对同一真实命令流、素材和 AXI 延迟模型比较 v14 模式与 v15 模式，逐帧核对 307200 个 RGB 像素。该测试不包含背景恢复、CPU 和显示竞争，不可把周期收益直接换算成实际弹数上限。

共享显示集成、异常响应、读取队列背压、缓存冲突、裁剪、跨 4 KiB、透明区、寄存器快照和旧模式回归分别检查。交付清单记录最终 bit、ELF 和源文件哈希。

未连接、复位或配置板卡。请使用 hardware/v15/ti60f225_oob.bit 和同包 lunaria.elf，再测实际活动元素数及 60 秒帧率。设置仍支持 64–4096，电脑与板端使用同一游戏配置；4096 是容量配置，绝非稳定 60 FPS 保证。超过 512 后的 CPU 分页仍可能成为瓶颈。

## 后续架构方向

本版没有实现目标画面 tile 缓存或分块合成，也没有改 CPU 分页总线。下一阶段应根据新计数决定：若目标读取仍主导，做保持命令顺序和逐像素舍入的片内 tile 合成，减少重叠精灵反复读写目标；若超过 512 后 CPU 更新耗时占主导，再实现批量分页传输。两者都需独立资源、时序及图像一致性验证。

## 本机已完成的验证记录

最终实现使用 25536 LUT4、214 RAM10；核心目标 100 MHz，分析 Fmax 126.839 MHz，30 项时钟关系最小报告裕量 0.026 ns。固件片内 RAM 含 8192 字节栈共 63552 字节，调试保留区前余量 960 字节。

共享通路通过 60 完整帧、1997602 像素检查。离线逻辑/命令一致性 64000 帧，512 槽及以下零弹池 DDR 访问检查 44800 帧，画面裁剪 200 次完整 RGB 对比，连续激光兼容性 4000 帧。读取预取还检查了目标 AR、源数据、目标数据分别超过看门狗阈值后恢复，确认排空未完成请求才结束命令。

相同 AXI 模型下，三个真实样例（活动弹数 473/546/829，绘制命令 512/575/824）的周期从 567100/628370/893408 降为 503104/556864/791863。目标读写拍数从 106468/117952/167728 降为 86618/95536/135995。周期下降约 11.3%–11.4%，目标读写减少约 18.6%–19.0%。该数据只用于局部实现比较，不代表上板帧率或最高元素数。
