# 常驻调试版与弹幕游戏

这次在 `advanced_demo` 的现有游戏上扩展，不改 `basic_demo` 或硬件 RTL。2026-10-24
用户已反馈通过桌面窗口加载 ELF 后游戏可以显示，背景跳变修复后显示正常。
UART 实际接收、调试命令、自测结果和持续帧率仍需保存板端验证记录。

与远端 Flash 功能合并后，默认构建启用 Flash。若使用原来的 v6 bit 和生成素材，
构建时加 `--define GAME_FLASH_ENABLE=0`，并用 `--ide-root` 指定本机 IDE 路径；
Flash 版另需带 SPI0 的硬件及正确素材，不能直接用原来的已封存图集替换或绕过验证。

## 先用起来

1. 板上需要已有 UART/Alpha/Color Key 的 advanced v6 位流。已加载正确位流时无需重新编译 FPGA。
   基础版位流不能直接运行高级游戏。调试窗口遇到硬件 ID/版本不匹配会拒绝加载。
2. 如果刚重新配置/烧录位流，先等板卡硬件初始化完成，再结束 RISC-V IDE 的 Debug 会话并退出 Programmer，释放 JTAG。
   重新配置会清空游戏 RAM 和硬件会话状态，因此之后要从窗口重新加载 ELF。
3. 双击 `advanced_demo/start_game_debug.cmd`。本机默认使用 `D:/Efinity/python311`，
   IDE 路径可在窗口中修改。其他电脑可用带 Tkinter 的 Python 3 运行 `tools/game_debug_window.py`。
4. 点击“连接 / 读取”。**连接不会加载或替换程序**。板上仍是旧程序时，会提示 ELF 不匹配，
   连接会保留，可以继续点击“加载并运行 ELF”。
5. 点击“加载并运行 ELF”，首次把新的常驻 ELF 放进 CPU RAM。无需先暂停旧游戏；工具会在受保护的 CPU DDR 会话结束后检查硬件边界，并等待绘图/交换操作排空，再写 RAM。程序从 `_start` 启动，
   检查素材和图集后进入游戏。初始化期间稍候再点“读取状态”。
6. 此后用“重开”“暂停”“继续”“应用”“一键自测”“进入游戏”操作，无需再加载 ELF。
   断电或重新配置 FPGA 后，需要重新加载程序。修改 C 源码后也需要构建和加载新 ELF。

源码目录里的默认 ELF 是 `software/interactive_demo/build/game/survival_game.elf`。
旧封存 ZIP 中的 ELF 和工具不会自动更新；本次请直接从源码目录运行窗口。
如需观察旧游戏，可选择当时实际加载的旧 ELF，连接后仅能读取原有状态。
不要只把新 ELF 换进旧封存包后继续照旧说明验证。

## 日常调试

- GAME OVER 默认显示倒计时，3 秒后自动新开；也可以松开后重新按射击键立即重开。
- “自动重开 ms”：0 关闭，其他值为 1–60000 ms；关闭时 GAME OVER 保持，等待重开命令/射击。
- “敌机上限”：1–48；调低会在安全边界移除超出上限的敌机。敌弹池固定最多 64 发。
- “敌弹间隔”：150–10000 ms；“子弹 Alpha”：0–255；无敌模式用于长时间观察与负载测量。
- 参数只在点击“应用”后生效，重开保留已应用参数。窗口初始显示默认值；
  连接已有程序时请先看状态日志里的实际参数，窗口输入框不会自动覆盖板上设置。
- “一键自测”暂停游戏流程，在后台缓冲区依次验证 FILL、Color Key 透明/实体像素、
  Alpha 的逐像素参考值和交换后的前台地址。测试后停在结果页，点击“进入游戏”开始新局。
  `self_test_result` 低 16 位为通过位，高 16 位为不匹配位：1=FILL、2=Key、4=Alpha、8=Swap。
  全通过是 `0x0000000f`。硬件超时或错误会进入故障状态，不会被标成测试通过。
- 输入观察不需要更换诊断 ELF：刷新 COM 列表、选择实际板卡串口、开始发送，再读取状态。
  只有板上 `uart_accepted` 增长且 `buttons` 随按键变化，才说明板卡实际收到了输入。
  电脑发送成功本身不能证明串口链路正确。坏 CRC、版本、标志、陈旧序号和超时释放计数也在日志里。
- 发送期间会锁定串口选择和刷新按钮；要试另一个 COM，先停止发送，等端口关闭后再选择并开始发送。
  多个 COM 都能打开，仅说明 Windows 允许写入，不能证明它们都连接了 FPGA 的 UART RX。
  窗口分别显示当前发送端口和最近一次板端接收快照；板端累计计数应连续读取比较，不能用旧累计值确认新端口。
- 如果日志显示 `Cannot open a`，端口框里误填了字母 `a`，Windows 根本没有打开串口；新版窗口只能从有效 `COMn` 下拉项中选择。点“刷新串口”，按设备管理器中连接板卡前后的变化选出板卡 UART 端口。游戏状态显示“检查素材”（phase 2）时先等初始化完成，直到“游戏中”（phase 4）再判断移动。
- 有效 COM 口已打开但 `uart_accepted` 仍为 0 时，先核对选中的是板卡 UART 通道而非其他串口。FT4232 的 UART 通道/COM 映射需按本机设备管理器确认；若 Windows 没有新增 COM 口，检查 USB 数据线和对应 VCP 驱动。
- 键盘仍用原来的 115200 8N1、6 字节 CRC 协议：WASD/方向键移动，空格/Ctrl 射击，P 暂停，
  Esc 停止发送。停止/关闭时发送松键；板上静默超时也会释放按键。
- “导出日志”保存状态、首个故障快照、原始硬件计数、命令确认和 OpenOCD 输出。

## 玩法变化

保留玩家射击、敌机、计分、生命和爆炸效果，增加敌方瞄准弹、三路扇形弹及其碰撞。
每 12 秒进入下一波，奇数波瞄准、偶数波扇形。玩家子弹为蓝色，敌弹复用已封存图集的橙色区域，
无需改写或绕过已经封存的素材。敌弹命中判定使用飞机中心 6×6 像素区域；
受击后有短暂无敌，敌机碰撞和漏过仍按原玩法扣生命。

运动/碰撞以 16 ms 固定步推进，渲染帧率降低时会追赶模拟。长时间停 CPU 后最多追赶
1024 ms，其余时长会平移游戏计时并累计到 `dropped_ms`，避免恢复时瞬间执行几分钟游戏。
这不代表渲染达到 60 FPS。实际精灵数按成功提交的精灵绘制命令统计，包含敌弹、玩家光晕和效果，
不把背景/HUD 的矩形算成精灵。

启动时会先把相同的暗色背景写入两个完整 1920×1080 显示缓冲，再开始局部游戏绘制。
原始测试彩条只初始化了前缓冲；若只画中间游戏窗口，双缓冲切换会让窗口外露出不同的旧内容。

## 测量帧率

1. 应用无敌模式，进入游戏；等敌机/弹幕达到要观察的数量，再点击“连续测量 60 秒”。
2. 窗口随后 62 秒不做 JTAG 读写。板上从处理命令时自行计时，保存至少 60000 ms 的区间结果。
   测量时游戏 P 键暂停和调试状态切换被屏蔽，移动/射击仍可使用。
3. 结束后窗口读取平均呈现 FPS、最低秒窗 FPS、整个区间的精灵最小/最大值、交换数和故障计数。
   只有 `measurement_state=2` 且命令已确认、没有错误，才是完整区间。

普通 JTAG 读取会短暂停 CPU，会标记 `measurement_disturbed`；默认没有周期性自动读取。
读取异常也会恢复原来运行的 CPU，原本暂停的 CPU 保持暂停。窗口期间以外的 IDE、调试器或其他
进程也可能干扰运行，测量时不要再启动它们。关闭窗口会结束这次观察，应重新开始完整区间。
“最高精灵数”只是区间峰值；要声明某个负载持续 60 FPS，还应确认精灵最小值和最低秒窗，
以及 underflow/missed/硬件错误没有增长。显示器 60 Hz 不等于游戏 60 FPS。

硬件错误、underflow、missed 都保留；首次故障快照不会被“重开”覆盖。固件发生硬件故障后拒绝
游戏命令，保持可读，不清除粘滞错误或强行交换缓冲。先导出日志再定位问题。
加载时也会检查硬件版本、空闲/缓冲所有权和 CPU DDR 会话；没有安全边界时不覆盖 RAM，超时会附上对应寄存器值。若发现 CPU DDR 会话故障位已锁存，工具会拒绝加载并提示重新配置位流，不会尝试清错。
若加载过程中通信失败，可能只写入了部分程序，此时 CPU 会保持暂停，需要重新加载完整 ELF。

## 本机复现检查

在 `advanced_demo` 下：

```powershell
$env:PYTHONHOME = 'D:/Efinity/python311'
& 'D:/Efinity/python311/bin/python.exe' -B scripts/build_apb_software.py --program game --ide-root 'D:/Efinity/efinity-riscv-ide-2026.1' --define GAME_FLASH_ENABLE=0
& .\scripts\run_interactive_checks.cmd
```

本机回归入口使用已安装的 VS 2022 C 编译器；其他电脑在 C 编译器环境下分别运行
`run_game_logic_checks.py`、`run_uart_keyboard_checks.py`、`run_game_debug_checks.py`。
调试检查需要先构建 ELF，并使用带完整 Tkinter/Tcl 的 Python。

离线检查覆盖固定步/时钟回绕/暂停、自动重开、敌弹/碰撞、双缓冲全屏背景初始化、命令序号和确认、运行状态恢复、
加载边界等待/排空/故障诊断、ABI/ELF 符号、界面构造、真实 OpenOCD Jim Tcl 配置解析（硬件调用替换为空操作）。
这些检查不等同于 JTAG 实连、板上像素读回、UART 接线或实际性能验收。
